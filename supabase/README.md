# Supabase

## Єдине правило

**Схема змінюється тільки файлом у `supabase/migrations/`.**

Supabase Studio — для читання, SQL-снипетів і налагодження (PRD §13.1). Перша ж
правка колонки мишкою розсинхронить dev і prod, і виявиться це на деплої.

```bash
npm run db:start                       # локальний стек у Docker
npx supabase migration new <назва>     # нова міграція
npm run db:reset                       # накотити все з нуля + seed.sql
npm run db:types:local                 # типи з локальної бази
npm run db:push                        # накотити міграції в linked-проєкт
npm run db:types                       # типи з linked-проєкту
```

Два скрипти типів навмисно: `--local` і `--linked` дають різний результат,
і мовчазна підміна одного одним — це порожній `database.generated.ts`
і нетипізовані запити по всьому застосунку.

`db:types` після кожної міграції, у тому самому коміті — це перевіряє
pre-commit хук.

Покрокове підключення хмарного проєкту і Google OAuth — `docs/supabase-setup.md`.

## Оточення

Два проєкти Supabase, обидва в регіоні **Frankfurt (eu-central)** — PRD §10.3.
Регіон не змінюється без міграції, а затримка реалтайму критична для гри
з таймером.

| Проєкт             | Призначення                           |
| ------------------ | ------------------------------------- |
| `inkoly-quiz-dev`  | розробка, `supabase link` вказує сюди |
| `inkoly-quiz-prod` | продакшн                              |

Безкоштовний тариф дозволяє рівно два активні проєкти — місця для окремого
staging не лишається.

⚠️ **Пауза безкоштовного тарифу.** Проєкт призупиняється після тижня без
активності і відновлюється вручну з дашборду. Для платформи, у яку грають раз
на місяць, це означає непрацездатний застосунок саме тоді, коли він потрібен.
Keep-alive задача потрібна до першої реальної партії, не «після фази 1».

## Що вже є

- `migrations/…_initial_schema.sql` — профілі і контент квізу: enum з повним
  переліком значень (§4.1), `profiles` з тригером створення при першому вході,
  `quizzes`/`stages`/`questions`/`question_options`/`media_assets`,
  політики доступу §11.3.
- `seed.sql` — демо-квіз і локальний ведучий `host@local.test` / `password123`.
  Виконується тільки при `db reset`, у хмару не потрапляє.

## Що тут ще з'явиться

- `rooms`, `participants`, `answers` і enum `room_state`. Залежать від трьох
  рішень у `docs/contract.md` — як автентифікуються учасники, звідки летить
  Realtime Broadcast, звідки береться серверний час. Закрити їх треба до цієї
  міграції, а не під час неї.
- Серверні функції §12 і санітизований зріз варіантів для учасників (§8.3).
- Планова задача закриття покинутих кімнат (§9.8, §13.1).
