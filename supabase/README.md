# Supabase

## Єдине правило

**Схема змінюється тільки файлом у `supabase/migrations/`.**

Supabase Studio — для читання, SQL-снипетів і налагодження (PRD §13.1). Перша ж
правка колонки мишкою розсинхронить dev і prod, і виявиться це на деплої.

```bash
npm run db:start                       # локальний стек у Docker
supabase migration new <назва>         # нова міграція
npm run db:reset                       # накотити все з нуля + seed.sql
npm run db:types                       # регенерувати типи в app/types/
```

`db:types` після кожної міграції, у тому самому коміті — це перевіряє
pre-commit хук.

## Оточення

Два проєкти Supabase, обидва в регіоні **Frankfurt (eu-central)** — PRD §10.3.
Регіон не змінюється без міграції, а затримка реалтайму критична для гри
з таймером.

| Проєкт             | Призначення                           |
| ------------------ | ------------------------------------- |
| `inkoly-quiz-dev`  | розробка, `supabase link` вказує сюди |
| `inkoly-quiz-prod` | продакшн                              |

Безкоштовний тариф дозволяє рівно два активні проєкти — місця для окремого
staging не лишається.

⚠️ **Пауза безкоштовного тарифу.** Проєкт призупиняється після тижня без
активності і відновлюється вручну з дашборду. Для платформи, у яку грають раз
на місяць, це означає непрацездатний застосунок саме тоді, коли він потрібен.
Keep-alive задача потрібна до першої реальної партії, не «після фази 1».

## Що тут ще з'явиться (день 1–2)

- `migrations/` — таблиці §11.1, enum з ПОВНИМ переліком значень (§4.1),
  політики доступу §11.3, серверні функції §12.
- `seed.sql` — демо-квіз для локальної розробки.
- Планова задача закриття покинутих кімнат (§9.8, §13.1).
